> [打包与文件所有权](PACKAGING.md)为准。

>
> 更新日期：2026-08-17

## 1. 文档目的

本文档固化 Steer 的产品目标、设计边界、已确认语义、开发顺序和验证要求。

它不是首版功能承诺。Steer 是个人需求优先的开源项目，开发必须从当前真实使用场景出发，按需递增，禁止为了构造“完整产品”提前实现尚无真实用例的能力。

候选上游核验已经完成。第一版按明确的需求场景实现最小闭环，不按其他插件的菜单数量定义范围。私人部署配置、迁移对照和实机审计记录不属于公开仓库内容。

## 2. 项目定位

### 2.1 核心目标

Steer 是面向 OpenWrt 的透明代理意图编译器和控制平面。

它要做到：

- 好用；
- 配置清晰；
- 指哪打哪；
- 保留真实 IP、UDP、QUIC 和 HTTP/3；
- 出现异常时能够明确说明原因；
- 不用隐藏规则、隐式 fallback 或虚假成功掩盖能力缺口。

Steer 不是 sing-box 原生 JSON 编辑器，也不是把已有代理插件换一套界面重新包装。

### 2.2 项目姿态

- 首先服务项目维护者明确提出并能够验证的需求。
- 可以开源，供少数具有相似需求的高级用户自行使用。
- 不主动追求用户增长。
- 不围绕社区热度扩展功能。
- 不承诺公共 SLA、广泛设备适配、长期旧版本支持或完整用户支持体系。
- 保留可复现构建和发布，是为了可靠维护自己的设备，而不是推动产品化扩张。

### 2.3 目标用户模型

用户理解节点、地区、TCP、UDP、DNS、规则和出口等基本概念，但不应被迫理解 sing-box JSON、nftables hook、fwmark、路由表或进程编排细节。

## 3. 最高优先级原则

发生目标冲突时，按以下顺序决策：

1. 正确性；
2. 可验证性；
3. 用户意图的确定执行；
4. 清晰和可维护性；
5. 可用性；
6. 性能；
7. 协议与设备覆盖范围。

以下问题必须阻止稳定版发布：

- 未声明的直连；
- 流量进入错误出口；
- DNS 路径与业务流量路径不一致；
- IPv6 绕过策略；
- 配置或运行失败被报告为成功；
- 受管流量绕过透明代理进入 flowtable；
- 受管 zone 中使用公网 IPv6 GUA 的客户端绕过 DNS 重定向；
- 无法解释的隐藏规则覆盖。

显式失败可以接受，但必须可见、可诊断并可恢复。

## 4. 明确不做的事情

- 不使用 Fake-IP。
- 不通过全局阻断 UDP/443 强迫 HTTP/3 降级。
- 不开放原生 sing-box JSON 作为配置逃生口。
- 不允许远程订阅或规则集改变本地路由动作。
- 不与 PassWall、PassWall2、OpenClash、HomeProxy 等其他透明代理同时接管流量。
- 不维护长期分叉的 sing-box 或 SmartDNS 核心。
- 不为了支持低配设备限制高配设备的缓存、并发和诊断能力。
- 不一次性实现所有讨论过的能力。
- 不把未验证的上游能力写成项目承诺。

## 5. 总体架构边界

### 5.1 Steer 拥有的部分

Steer 应拥有：

- LuCI 交互界面；
- UCI 语义配置模型及版本迁移；
- 节点和订阅管理；
- 逻辑出口模型；
- DNS Profile；
- 统一 DNS 与路由规则；
- 高级规则 DSL 及语义 AST；
- 配置编译、校验、差异展示、原子应用和回滚；
- OpenWrt 服务、防火墙、路由和 DNS 挂接；
- 运行状态、短时诊断与 Why? 解释；
- 配套核心版本及能力矩阵；
- 签名软件源和可复现构建。

### 5.2 上游核心拥有的部分

sing-box 负责实际透明代理、协议实现、流量转发和其原生支持的嗅探与路由能力。

SmartDNS 负责其已验证支持范围内的 DNS 上游访问、缓存和地址质量选择。

两者必须保持上游原样。Steer 只支持经过验证的配套版本。用户可以自行替换二进制，但这种组合属于不受支持状态，并应在诊断页明确显示。

如果上游原样无法实现某项 Steer 语义，处理顺序是：

1. 判断控制层能否无歧义实现；
2. 若不能，则从当前版本删减或延后该能力；
3. 等待或推动上游提供能力；
4. 不以长期私有核心补丁维持功能幻觉。

### 5.3 第一版上游基线

第一版采用产品级 fork 路线：以 OpenWrt-momo 的 procd、firewall4、双栈 TPROXY 和 zone 到实际设备解析方式作为主要工程参考，但由 Steer 自己实现 UCI 意图模型、引用校验、编译、事务和 LuCI。Steer 不接收整份 sing-box JSON，也不继承 Momo 的 Fake-IP、Dashboard、隐式中国大陆绕过或远程配置模型。

PassWall2 只作为公开代码层面的对照来源，不是运行时或 LuCI 输入。HomeProxy 只用于核对节点字段与 sing-box 配置形态，不复制其 GPL-2.0-only 代码。详细结论见 `docs/UPSTREAM_BASELINE.md`。

GeoSite/GeoIP 使用 `Loyalsoldier/v2ray-rules-dat` 的发布数据。完整 `geosite.dat` 与
`geoip.dat` 由独立、版本锁定且固定哈希的 `steer-geodata` 包提供。版本更新只通过包管理器
完成；Steer 不在运行时查询 release 或下载替换 `/usr` 数据。

Steer 按当前配置引用的分类把包内数据转换为 `/var/lib/steer` 下的本地 `.srs`。每个新包
版本都必须让所有已启用且被引用的分类完成转换、编译和校验；任一分类失败或消失时，Apply
明确失败并保留当前运行代。数据只提供匹配集合，不能定义规则顺序、DNS Profile、Route 或
fallback。

DNS 接管不再猜测或解析受管客户端。Steer 使用全局双栈入口接管 TCP/UDP 53，并用独立测试覆盖公网 IPv6 GUA 客户端。

## 6. 核心语义模型

### 6.1 节点

节点描述单个远端代理实例及其实际能力。能力不能压缩成一个 `udp=true`，至少需要区分：

- TCP 转发；
- UDP 转发；
- 原生数据报；
- UDP over stream；
- 外层 QUIC；
- TLS、Reality、Vision 等传输或安全特征。

### 6.2 逻辑出口

规则只能指向逻辑出口，不直接依赖订阅节点的短期身份。

设计能力上限包括：

- 单节点；
- 按优先序选择首个健康节点的故障转移；
- 按新流加权分配；
- 按客户端或目标做一致性哈希。

“优先级切换”和“容灾切换”不拆成两个含义模糊的模式。

节点健康状态按所需能力分别维护，例如 TCP 正常不能证明 UDP/数据报正常。主动探测与真实连接失败可以共同参与健康判断，但阈值、冷却、恢复和切换原因必须可解释。

切换只影响新流。Steer 不承诺把已经建立的 TCP、UDP 或 QUIC 流无损迁移到新节点。

多节点出口中的 DNS 查询与随后业务连接应保持实际节点亲和，避免 DNS 获得的 CDN 地址与业务出口地域不一致。该能力是否能在不修改核心的前提下实现，尚待验证。

### 6.3 DNS Profile

DNS Profile 明确描述：

- 对应的独立 SmartDNS 实例、监听端口和缓存；
- 使用哪些上游 DNS Server；
- 有序后备解析器；
- 全部失败后的终止行为；
- 缓存边界。

一条规则只选择一个 DNS Profile，不直接选择 DNS Server。每个 DNS Profile 由 Steer 生成并管理一个 SmartDNS 运行实例；实例内部的响应模式、地址测速和 fallback 由该 Profile 的显式 SmartDNS 设置决定。不同 Profile 使用独立监听端口、配置、缓存和进程状态。

禁止全局隐藏 DNS fallback。

Bootstrap DNS 是启动根：只能使用 IP 字面量，由 SmartDNS 和 sing-box 携带核心绕行 mark 直接访问，不允许选择代理出口。系统 NTP 同样是建立 TLS、Reality、证书校验和订阅访问之前的启动依赖；路由器本机发起的 UDP/123 必须在 output 接管入口固定直连，不能依赖尚未可用的代理核心或用户规则。

除 Bootstrap 外，所有 SmartDNS 业务上游都是路由器本机连接，与普通本机应用共用 output TPROXY 与普通 Rules。Steer 不生成内部 SOCKS、不创建专用入口，也不为 DNS Server 保存第二套出口字段。如果需要指定某个上游的出口，用户就在普通 Rules 中按其 IP/CIDR、端口和网络类型表达。

为避免 SmartDNS 的 UDP/TCP 53 业务上游被本机 DNS 劫持再次送回 Steer，SmartDNS 只为业务上游设置一个位于 TPROXY mark mask 之外的防回环 mark。nftables 只用它跳过本机 53 端口再劫持；output TPROXY 仍保留该 mark 并将连接送入普通 Rules。Bootstrap 另行携带核心绕行 mark 直连。因此启动依赖仍保持单向：`Bootstrap 直连 → sing-box 与 SmartDNS 启动 → 业务上游 output TPROXY → 普通 Rules → 逻辑出口`。

业务 DNS 缓存原则上按 DNS Profile 与实际出口路径隔离。SmartDNS 是否能原样满足这一要求，尚待验证。

### 6.4 统一规则

一条业务规则同时决定：

- 匹配条件；
- DNS Profile；
- 逻辑出口。

同一规则按用户确认的“混合规则”模型编译为两个可见投影：

- DNS 投影只使用查询阶段可观察的域名和客户端地址条件，选择该规则的 DNS Profile；
- Route 投影使用域名、客户端地址、目标 IP、TCP/UDP 和端口等全部条件，选择该规则的逻辑出口；
- 如果一条规则只有连接阶段条件，它不会生成空 DNS 规则，DNS 会继续从下方规则匹配，直到 Default；
- UI 必须明确显示上述差异，不能让一个不会参与 DNS 匹配的端口字段看起来会影响 DNS。

规则严格从上到下执行，第一条命中后停止。所有业务流量，包括 SmartDNS 上游，共用“普通 Rules → Default”这一个顺序。

规则表末尾必须存在用户可见、不可越过的 Default 规则。Default 的 DNS、出口和故障行为必须明确。

普通规则默认采用：

- 字段之间 AND；
- 同一字段中的多个值 OR。
- “域名匹配”统一承载裸关键词、`full:`、`domain:`、`regexp:` 与 `geosite:`；
- “目的 IP 匹配”统一承载 IP/CIDR 与 `geoip:`；
- 编译器必须用内层 logical OR 和外层 logical AND 显式表达上述关系，不能依赖 sing-box 对不同匹配项的默认关系。

不使用否定条件堆叠普通规则。简单例外应通过前置正向规则表达。

高级用户可以使用 Steer 自有文本 DSL 表达任意布尔条件。DSL 必须：

- 编译成稳定、带版本的语义 AST；
- 与普通规则使用同一匹配语义；
- 进行完整语法和类型校验；
- 能被 Why? 逐节点解释；
- 不允许插入任意 sing-box JSON。

高级 DSL 属于设计能力，不是默认首版要求。只有当前实际配置需要超出普通规则的表达力时才进入开发计划。

### 6.5 客户端身份

设备策略可以使用源 IP/CIDR 或源 MAC。源 MAC 在受管 LAN 的 ingress 上按以太网头直接匹配，
不解析为邻居表中的当前 IP，因此同一规则自然覆盖 IPv4、IPv6、SLAAC 和临时地址。MAC 只描述
当前二层链路上的客户端，不承诺跨路由、隧道或 MAC 随机化后的持久身份。

UCI 字段固定为 `source_mac_address`，与 sing-box 1.14 的原生规则字段同名。当前 sing-box 1.13
基线由 nftables 把每个 MAC 降级为专用双栈 DNS/TPROXY inbound；切换 1.14 原生能力时只替换
编译后端，不迁移用户规则。外部后端不得使用 MAC→IP 邻居解析，也不隐式修改 DHCP 静态租约。
源 MAC 与本地代理 inbound 属于互斥的流量来源，不能在同一规则中组合。

### 6.6 第一版 LuCI 信息结构

第一版界面采用以下入口：

- Overview：运行状态、全局入口范围、Bootstrap DNS 和收起的运行高级参数；
- Rules：可拖动的统一规则表，行内只呈现“匹配、DNS Profile、逻辑出口”，其余匹配字段进入编辑框；
- Local Proxies：具名 SOCKS、HTTP 或 mixed 入口，不直接绑定节点；
- DNS：DNS Profile 与上游 DNS Server 分成两个对象表；
- Nodes & Routes：节点凭据与逻辑出口分离，业务规则不直接引用物理节点；单节点分享 URL 在浏览器本地解析，先脱敏审查再进入 UCI 待提交变更；
- Rules 使用两个多行 IDE 式编辑器；编辑当前行时动态补全当前数据中的合法 Geo 名称。内部 sing-box 规则集由编译器自动去重生成。Default 固定在普通规则末尾，只能选择 DNS Profile 和 Route。
- UCI section ID 是跨节点、路由、规则、DNS 与本地入口共享的内部主键，由 UCI 统一生成。用户只填写名称；改名不改变 ID 或引用，任何页面都不得要求用户分配 ID。

界面的识别性元素是“Match → DNS Profile → Route”路径，它编码真实执行语义，不是装饰。表格只保留决策所需列，协议细节与运行 mark 不挤占主路径。LuCI 通过 `luci.steer` 最小权限 RPC 调用后端校验和事务 Apply，不获得任意命令执行权限。

当前界面仍缺少订阅 URL 导入与更新、Why? 和变更摘要，这些不能被现有 CRUD 表单或单节点分享 URL 解析冒充为已完成。私人部署配置与迁移对照必须保留在公开仓库之外。

### 6.7 本地代理入口

Steer 提供本地 SOCKS/HTTP 代理能力，但不采用“一个监听端口直接绑死一个节点”的模型。本地代理入口是具名对象，规则可以把该入口作为匹配维度，再按同一 First Match Wins 顺序选择 DNS Profile 和逻辑出口。

软件包默认不开放本地代理端口。新增本地入口必须由用户显式操作；SmartDNS 业务上游作为本机流量进入普通 Rules，不依赖内部 SOCKS 入口。

## 7. Real-IP、嗅探与域名证据

Steer 采用 Real-IP 路线，并承认透明代理不一定总能取得域名。

- 传统 TCP/UDP 53 DNS 可以接管。
- 不默认阻断或改写客户端自带的 DoH、DoT、DoQ。
- 使用加密 DNS且无法取得域名的连接，继续按目标 IP、协议、端口、设备和 Default 匹配。
- 不增加特殊的“域名未知”默认规则。
- DNS 反向映射与连接嗅探冲突时，优先使用当前连接中实际嗅探到的 TLS SNI、HTTP Host 或 QUIC 信息，并记录冲突。
- 嗅探只观察，不终止、不改写、不验证连接真实性。
- 嗅探失败、伪装 SNI 或 Tor 类流量不得因为诊断逻辑而被破坏。

## 8. 故障与 fallback 语义

不存在全局、隐藏的“代理失败就直连”或“全部失败就阻断”。

每个逻辑出口必须显式决定失败后：

- 阻断；
- 直连；
- 转向指定备用出口。

每个 DNS Profile 同样拥有自己的显式后备链和终止行为。

当系统既没有有效运行配置，也无法恢复 last-known-good 时，项目维护者已明确选择故障
关闭：保持局域网和管理面可用，但继续接管并阻断无法按策略处理的 WAN 流量。核心或任一
DNS Profile 持续不可用时不得撤销规则形成未声明直连。Bootstrap DNS、系统 NTP、本地与
非全局目标仍使用固定救援路径。运行状态必须明确显示阻断原因，不能只以连接超时表达故障。

## 9. 系统流量与自救不变量

路由器自身的普通业务流量与 LAN 客户端使用同一套规则。Steer 提供一个默认开启的
“代理路由器本机”总开关：开启时同时接管本机公共 TCP/UDP 与传统 UDP/TCP 53 DNS，
关闭时两者都不接管，不能形成只代理业务连接却暗中保留系统 DNS 的半接管状态。
传统 53 劫持先于目标地址旁路执行，因此发往 `127.0.0.1:53` 或 `::1:53` 的本机查询
也进入 DNS Profile；这是保留地址边界唯一的端口级入口，不意味着其他回环流量被代理。
本机 output 接管必须排除 conntrack reply，避免路由器本地服务对外部客户端的回包被误判
为新发起连接；该方向判定不是用户规则，也不能用于绕过本机主动建立的连接。

IANA IPv4/IPv6 Special-Purpose Address Registry 中 `Globally Reachable` 不为 `True` 的
目标前缀必须在 nftables 前置旁路，完全不进入 sing-box。清单由 Steer 构建时固化，记录
IANA 注册表日期并随 Steer 版本评审更新，不能由路由器运行时联网改变。Rules 页在所有
用户规则之前显示不可排序、不可关闭的“系统自救直连”，可展开查看覆盖范围和命中计数。
系统 NTP 例外只覆盖路由器本机发起的 UDP/123；LAN 客户端访问 UDP/123 仍按普通 Rules
执行，不能借此绕过用户策略。

以下最小集合必须使用可见但不可关闭的非递归路径：

- 节点和 DNS 上游地址的 Bootstrap；
- 系统校时；
- 代理核心自身出站的防回环；
- Steer、sing-box、SmartDNS 之间的本机 IPC；
- DHCP、RA、NDP 等链路维护流量。

订阅更新、Steer 更新和路由器上的普通应用不属于强制直连例外，仍按统一规则处理。

后续审计还需确认 WAN DHCP/PPPoE、DHCPv6、必要的 ICMP/ICMPv6、健康检查和恢复入口是否已被上述分类完整覆盖。

## 10. 订阅和远程规则集

### 10.1 订阅权限

订阅是不可信的节点数据源，只能新增、更新或标记删除节点。它不能修改：

- 逻辑出口；
- DNS Profile；
- 业务规则；
- fallback；
- 系统策略。

合法的定时更新经过解析、能力校验和生成校验后自动原子生效；失败时保留上一版本并告警。

订阅删除仍被逻辑出口引用的节点时，保留节点的旧快照并标记“订阅已移除”，直到用户替换或显式删除。

混合订阅中，受支持项目可以生效；不支持或解析失败的项目必须逐项报告原因，不能静默忽略，也不能伪装成完整成功。

### 10.2 远程规则集权限

远程规则集只能更新域名或 IP 等匹配数据。本地规则始终决定顺序、DNS、出口和故障语义。

规则集更新必须原子生效并保留 last-known-good。

## 11. 协议策略

设计范围包括常见分享链接：

- VLESS，包括 Reality、Vision 等组合；
- VMess；
- Trojan；
- Shadowsocks；
- Hysteria2；
- TUIC；
- 配套 sing-box 稳定支持且经过完整验证的 AnyTLS、ShadowTLS 等新协议。

SSR、Hysteria1 和 WireGuard 不作为默认公网抗审查节点协议目标。

上述列表是能力核验范围，不是首版必须一次实现的列表。首版只实现已公开声明并完成验证的协议，以及构成最小闭环不可缺少的协议。

协议一旦被配套上游移除或确认不再安全，Steer 不维护私有兼容实现。稳定版升级必须预检现有配置；发现将失效的节点时阻止普通升级并说明影响，只有用户显式强制升级才允许其失效。

## 12. OpenWrt 集成

### 12.1 支持范围

- 首个支持基线为 OpenWrt 25.12 及以上。
- 仅预设支持 64 位架构。
- 不预先承诺固定内存下限或具体设备名单。
- 资源支持范围必须由真实设备和代表性压力测试决定。
- 低配设备可以使用收缩后的缓存、并发和诊断预算；高配设备应能扩大这些预算。

### 12.2 全局透明代理边界

Steer 不再解析或维护 OpenWrt firewall zone。启用 Steer 后，DNS 规则在 `inet` 表中全局接管所有入口和
路由器自身的 TCP/UDP 53；这意味着 WAN 入站 DNS 也会被重定向，风险由用户明确承担。源 MAC 规则同样
使用全局 ingress，不绑定接口；普通私网、本地、广播和组播目的地仍按既有排除语义绕行。

源 MAC 分类必须位于同一个 `table inet` 接管边界中，在协议族判断前用 `ether saddr` 选择专用
入口；IPv4 与 IPv6 不得生成两套语义不同的设备规则。未命中 MAC 专用入口的流量继续进入通用
双栈入口。

### 12.3 与其他代理插件的关系

Steer 排他拥有透明代理链路。启用前需要检测：

- 冲突服务；
- 监听端口；
- nftables/iptables 规则；
- fwmark 与策略路由；
- TUN 设备；
- DNS 接管链路。

发现冲突时解释并拒绝启用。Steer 不自动关闭或修改其他插件配置。

### 12.4 Flow offload

Steer 不应全局修改用户的软件或硬件 flow offload 开关。

目标行为是：

- 受管流量在进入 firewall4 flowtable 前被透明代理接管；
- 明确直连和未托管流量仍可进入 flowtable；
- Apply 和启动检查验证受管流量不会旁路；
- 在特定内核、驱动或硬件平台上无法证明隔离时，拒绝启用并说明原因。

这一设计参考 PassWall2 当前在 `prerouting` 提前接管、firewall4 在 `forward` 阶段加入 flowtable 的结构，但必须通过 OpenWrt 25.12 实机验证，不能只凭规则顺序下结论。

## 13. 配置事务和恢复

LuCI 编辑先进入草稿。只有用户点击 Apply 时才执行：

1. 校验 UCI 语义配置；
2. 编译生成配置；
3. 校验 sing-box、SmartDNS、防火墙和路由配置；
4. 展示有意义的变更摘要；
5. 原子切换运行状态；
6. 验证本地不变量；
7. 成功后保存 last-known-good；
8. 失败时恢复上一运行状态。

自动回滚依据本地可验证条件：

- 配置是否合法；
- 进程是否就绪；
- 端口和 IPC 是否存在；
- 路由、mark、防火墙和 DNS 链是否符合预期；
- LuCI 管理入口是否仍可达；
- flow offload 隔离是否成立。

公网网站或公共 DNS 暂时不可达不能单独触发配置回滚，以免把上游故障误判为本地配置错误。

第一版运行层已实现其中的最小闭环：候选目录、UCI 语义检查、`sing-box check`、使用临时表名的 `nft -c`、procd 实例存活检查、Steer nft 表检查和 last-known-good 编译产物。SmartDNS 缺少可靠的离线配置检查命令，当前通过严格生成和切换后的实例存活检查处理，不能在界面上标成“已原生预检”。端口就绪、LuCI 可达性、flow offload 隔离和故障注入回滚仍是未完成验收项。

停用或普通卸载必须撤销进程、nftables、策略路由和 DNS include 等运行状态，但保留 Steer 语义配置与凭据。只有显式清除数据才删除配置、缓存和快照。

## 14. 诊断与 Why?

Why? 不是独立实现的第二套路由器。它必须复用与配置编译相同的语义 AST 和规则解释器。

诊断需要区分：

- 静态预测：根据当前配置和给定输入推导将命中哪条规则；
- 运行证据：根据实际连接、DNS 反向映射、嗅探、节点选择和日志说明发生了什么。

两者不能混为一谈。

默认只保留短时、有界、脱敏的环形摘要。完整 debug 必须由用户临时开启、自动过期，并在导出前检查域名、IP、设备信息和凭据泄漏。

## 15. 安全与隐私

- 信任拥有路由器 root 权限的管理员。
- 节点密钥和订阅地址使用 root-only 文件权限保存。
- LuCI 默认遮罩凭据。
- 普通日志、诊断包和普通配置导出不得包含凭据。
- 用户可以显式导出明文完整备份；界面必须明确警告该文件含全部凭据并要求用户自行保护。
- 项目不包含遥测。
- 版本检查、规则集更新等项目侧联网功能必须由用户显式启用并显示目标地址。

## 16. 发布与升级

- 使用自有签名 apk 软件源。
- 提供稳定轨和预览轨。
- 默认使用稳定轨。
- 软件源发布 Steer 与配套 sing-box、SmartDNS 的已验证组合。
- 发布基础设施服务于个人设备的可复现部署，不构成公共 SLA。
- UCI 语义配置带 schema 版本并自动向前迁移。
- 生成配置是临时产物，可以随时重建。
- 不承诺旧版本读取新 schema，也不为了降级兼容长期保留旧模型。

## 17. 稳定版验证门槛

稳定组合至少需要覆盖：

- IPv4、IPv6 和双栈；
- TCP、UDP、QUIC/HTTP3；
- 当前支持的每种节点协议；
- DNS 与业务出口一致性；
- DNS fallback、缓存隔离和 Bootstrap；
- 单节点、故障转移和已实现的负载均衡模式；
- 节点 TCP/UDP 分能力健康；
- 订阅部分成功、节点删除和原子回滚；
- 配置升级、失败 Apply、进程崩溃和开机恢复；
- 其他代理冲突检测；
- 来自每个受管 zone 的 IPv4、ULA、link-local 和 GUA 客户端对公共 IPv4/IPv6 DNS 发起 UDP/TCP 53 查询时均进入 Steer DNS 链，WAN ingress 不得进入；
- 同一源 MAC 的 IPv4、IPv6、SLAAC 与临时地址同时命中所选 DNS Profile 和 Route，其他 MAC 继续按后续规则执行；
- IPv6 委派前缀变化、接口重建和防火墙 reload 后，受管 zone 的 DNS 接管语义保持不变；
- flow offload 旁路检查；
- 凭据、日志和备份边界；
- 代表性资源压力；
- 至少一组代表性实机长时间稳定运行。

没有实际执行上述验证时，不得声称对应能力已支持或稳定。

## 18. 开发阶段

### 阶段 0：建立需求与边界

目标是建立可公开复现的需求与验收边界，而不是罗列其他插件的全部菜单。

需要确认：

- OpenWrt 与配套核心的支持版本；
- 当前使用的核心及版本；
- 已安装的协议组件；
- 需要覆盖的节点协议和传输组合；
- TCP、UDP、IPv6、DNS、本机代理和 ACL 设置；
- 订阅数量、更新方式和节点引用关系；
- 分流规则、规则集和默认出口；
- 自动切换、探测和故障行为；
- 与 SmartDNS、dnsmasq、firewall4、DHCP 和 flow offload 的关系；
- 哪些功能进入公开能力范围，哪些明确延后。

输出物：

- 支持功能清单；
- 非目标功能清单；
- Steer 最小替换闭环；
- 配置数据模型；
- 可复现验收用例。

阶段 0 的公开输出只保留产品不变量、通用能力矩阵和使用保留地址的测试场景。任何来自私人路由器的规则名称、节点、端口、地址、订阅关系、流量统计或迁移结论都不得进入仓库、测试 fixture、提交信息或 Release 资产。

### 阶段 1：上游能力与 fork 核验

基于阶段 0 的公开需求，而不是完整设计上限，比较候选上游：

- PassWall2；
- OpenWrt-momo；
- HomeProxy；
- 必要时其他更小的 OpenWrt 控制层实现。

同时验证未修改 sing-box 和 SmartDNS 能否满足最小闭环，形成逐项证据矩阵。

输出物：

- 上游选择与拒绝理由；
- 许可证兼容结论；
- 可复用代码范围；
- 必须删除的旧抽象；
- 不可实现或需要延后的能力。

### 阶段 2：最小可用闭环

只实现最小可用闭环所必需的功能，至少包含：

- 已声明支持的节点协议；
- 节点与逻辑出口；
- 可组合的 DNS Profile；
- 统一规则和可见 Default；
- 双栈透明接管；
- 原子 Apply、回滚和 last-known-good；
- 必要订阅解析；
- 在合并的域名和目的 IP 字段中动态补全 GeoSite/GeoIP 分类，并从版本化数据包自动生成内部规则集；
- 冲突检测和最小诊断。

不因架构已经预留扩展点而提前实现所有出口模式、协议或 DSL。

### 阶段 3：按真实需求递增

只有出现可复现、持续存在的实际需求时，才考虑增加：

- 高级规则 DSL；
- 被动健康摘除；
- 加权负载均衡；
- 一致性哈希；
- 更多协议；
- 更细的 Why? 运行证据；
- 更广的设备和性能档位。

每项新增能力都必须先回答：

- 当前哪个真实场景需要它；
- 上游原样是否支持；
- 失败时如何表现；
- 如何验证；
- 是否会破坏现有清晰模型。

## 19. 当前待核验问题

1. 未修改 sing-box 是否能实现主动与被动健康组合。
2. sing-box 是否能按 TCP、UDP/数据报能力分别维护可用性。
3. sing-box 原生出口组合能否提供加权分配和一致性哈希。
4. DNS 查询和业务连接能否保持同一实际节点亲和。
5. SmartDNS 能否按 DNS Profile 与实际出口身份隔离缓存。
6. SmartDNS 的显式 fallback 是否会产生隐藏的系统级降级。
7. OpenWrt 25.12 上 TUN `auto_route`、`auto_redirect` 与自定义 fw4 接管方式哪个更适合 Steer。
8. 软件和硬件 flow offload 在代表性设备上是否会旁路受管流量。
9. 路由器自身流量进入统一规则时，最小防回环集合是否完整。
10. 候选上游许可证和代码组合是否允许形成单一、清晰的 Steer 项目。
